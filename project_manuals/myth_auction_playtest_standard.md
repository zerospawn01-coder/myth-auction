# MYTH AUCTION 正式プレイテスト基準 v1.0

| 項目 | 内容 |
| --- | --- |
| 文書状態 | **Normative（正式基準）** |
| 採用日 | 2026-07-30 |
| 対象 | MYTH AUCTION の自動検証、擬似初見テスト、人間による初見テスト |
| 正本 | `project_manuals/myth_auction_playtest_standard.md` |

本書は、MYTH AUCTION のプレイテスト開始条件、実施順、記録方法、合否判定を定める。
本書の採用は各Gateの合格を意味しない。前段Gateが不合格の場合、後段Gateの結果を正式な合格根拠として扱わない。

## 1. テスト方式

### 1.1 擬似初見テスト

設計情報を知る開発者またはAIが、次の制約下で行う。

- 仕様書、コード、テストfixture、正解手順を参照しない
- セーブデータとテスト用ユーザーデータを初期化する
- 起動後に画面へ表示された情報と、操作後の反応だけを根拠にする
- 開発者用ショートカット、デバッグ操作、内部IDを利用しない
- 迷った場合も正解手順を調べず、迷った地点と試行を記録する

擬似初見テストは反復可能な事前検証であり、人間の初見理解を代替しない。最終的なUX受入には、設計・実装に関与していない人間の初見テストを組み合わせる。

### 1.2 Fresh profileの作成

擬似初見および人間初見の開始前に、通常プレイ用profileを削除せず、テスト専用の独立ユーザーデータ領域を作る。

1. ゲームを終了する
2. Commit SHA、ビルド、Godot versionを記録する
3. テスト専用の新しいOSユーザー、サンドボックス、または独立したGodot user-data rootを割り当てる
4. その領域に `user://episode_ma001_research_case.json` が存在しないことを確認する
5. ゲームを起動し、初期状態であることを画面から確認する
6. Session IDとuser-data rootの識別子を記録する
7. セッション終了後、その領域を再利用しない

既存profileからセーブファイルだけを手動削除する方法は、他の永続状態が残る可能性があるため正式手順にしない。自動テストでは `.github/scripts/run-godot-tests.ps1` がスイートごとに独立したuser-data rootを作成する。

### 1.3 人間の初見テスト

- 完成手順を事前に教えない
- 課題は目的だけを伝え、操作方法は伝えない
- 観察者は進行不能が確定するまで介入しない
- 発話、迷い、誤操作、期待した結果を要約せず記録する
- セッション間で案件、初期資金、画面順、審査条件を変更しない

MA-001 の詳細記録には `project_manuals/ma001_device_ux_session_sheet.md` を使用する。

## 2. Playtest Gate運用原則

実施順は次の通りとする。

1. Playtest Gate 0：動作基盤
2. Playtest Gate 1：擬似初見理解
3. Playtest Gate 2A：現行MA-001ループを独立3セッション
4. Playtest Gate 2B：製品版の購入・所蔵ループを連続3周
5. 保存・終了・再起動・再開
6. 画面サイズと最大負荷の差分確認
7. Playtest Gate 3：判断の面白さ
8. Playtest Gate 4：継続動機
9. 人間の初見テストによる再検証

判定はFail-Closedとする。必要な記録がない項目、再現不能な項目、判断不能な項目は合格にしない。

## 3. Playtest Gate 0：動作基盤

UX評価を開始する前に、次の条件をすべて満たす。

- CIが発見する正規テスト `tests/*_test.gd` が全件PASSする
- 採用時基準の53スイートを下回らず、将来追加された正規テストも全件実行する
- 正規スイートの失敗、エラー、タイムアウト、skip、allowlist、quarantine、除外が0件である
- clean checkout後のGodot importが成功する
- 初期化、保存、終了、再起動、再開が正常に完了する
- 状態遷移、資源、TraceLedger、保存データに不整合がない
- 各テストが独立したユーザーデータ領域を使用し、次のスイートまたはセッションへ状態を残さない
- テスト終了コードとGitHub Actionsの結果が一致する

`tests/test_val_only.gd` は正規スイートのglobに一致しない開発診断スクリプトであり、除外テストには数えない。正規テストをこの名前へ変更してGate 0を回避してはならない。

CIの基準runtimeは `.github/workflows/godot-headless-tests.yml` の `GODOT_VERSION` とする。擬似初見・人間初見も原則として同じstable runtimeを使用し、異なるversionを使う場合は別セッションとして差分を記録する。`project.godot` のfeature metadataと受入runtimeが異なる間、その差を合格判定から省略しない。

### Playtest Gate 0の証跡

合格記録には次を残す。

```text
Commit SHA:
GitHub Actions run URL:
Godot version:
検出スイート数:
PASS:
FAIL:
ERROR:
TIMEOUT:
SKIP / EXCLUDED:
Artifact URL:
保存・再開確認:
状態汚染確認:
判定:
```

GitHub Actionsが赤い状態、または53本未満しか検出していない状態では、Playtest Gate 1以降へ進まない。UI上の詰まりとコード上の不具合を区別できないためである。

`tests/visual_log/` はWindows runtimeの視覚証跡であり、headless CIまたは人間のUX合格を代替しない。`project_manuals/baselines/` は画面差分用の基準画像であり、操作理解の証跡とは分けて扱う。

## 4. Playtest Gate 1：初見理解テスト

説明を先に読まず、起動後の画面だけで判断する。

### 確認項目

- 何をするゲームなのか分かるか
- 最初に押すべき場所が分かるか
- 現在の目的と状態が読み取れるか
- 押せる要素と表示だけの要素を区別できるか
- 専門用語が説明なしで理解できるか
- 危険な操作や取り消せない操作が判別できるか

### 暫定合格基準

- **30秒以内**に最初の意味ある操作ができる
- **3分以内**に主要ループへ入れる
- 完成手順または開発者知識による誘導を必要としない
- PT-S0、PT-S1が0件である

「意味ある操作」は、画面を眺める、無目的にタブを切り替える、設定を開くことではなく、案件の状態またはプレイヤーの判断材料を前進させる操作を指す。

## 5. Playtest Gate 2：操作ループテスト

Gate 2は、現行vertical sliceと製品版の対象ループを混同しない。

### Gate 2A：MA-001研究・出品者ループ

現行MA-001では、fresh profileから次の流れを独立した3セッションで完走する。

> 出品物を受領する<br>
> → 観察・資料から情報とEvidenceを得る<br>
> → 研究・委託・矛盾解決で判断材料を作る<br>
> → ClaimとWarrantを構築して審査する<br>
> → 出品・保留・返却などの処分を決める<br>
> → NPC入札者の反応と結果を確定する<br>
> → 信用・人脈・履歴・保存への反映を確認する

3セッションでは、同じ終端だけを繰り返さず、異なる処分または調査判断を選ぶ。現行MA-001は連続3案件を提供しないため、3セッションを「連続3オークション」と報告しない。

### Gate 2B：購入・所蔵・次案件ループ

製品全体の受入では、次の流れを開発者知識に頼らず連続3周完走できるか確認する。

> 出品物を確認<br>
> → 情報・証拠を調べる<br>
> → 真贋・危険性・価値を判断する<br>
> → 購入または入札する<br>
> → 結果を確認する<br>
> → 所有物・記録・報酬への反映を確認する<br>
> → 次の出品物を選ぶ

プレイヤー自身の購入・入札、所蔵、次案件選択UIが未実装の間、Gate 2Bは **NOT IMPLEMENTED** と記録する。MA-001 vertical sliceのGate 2A判定には影響させないが、MYTH AUCTION製品全体のGate 2合格にはしない。

各周回では、成功経路だけでなく、見送り、資金不足、情報不足、失敗または不利な結果からの復帰も観察する。

### 操作記録

問題または迷いが発生した操作ごとに、次を記録する。

```text
Session ID:
周回:
時刻:
画面／状態:
プレイヤーがしようとしたこと:
期待した結果:
実際に起きた結果:
迷った箇所:
誤操作:
戻り方が分かったか:
問題の重大度:
修正案:
```

### Gate 2Aの合格条件

- 3セッションすべてでMA-001ループを進行不能なく完了する
- 結果が記録、資源、信用、人脈、履歴へ一貫して反映される
- 操作後に「何が変わったか」を画面だけで説明できる
- 誤操作後の復帰方法が見つかる
- PT-S0、PT-S1が0件である

### Gate 2Bの合格条件

- 連続3周で購入・入札から次案件選択まで完了する
- 所有物、記録、報酬、資金が一貫して反映される
- 見送り、資金不足、不利な結果から復帰できる
- PT-S0、PT-S1が0件である

## 6. Playtest Gate 3：判断の面白さテスト

単に情報を集めて一意の正解を探す作業になっていないかを評価する。

- 価格と価値の間で迷えるか
- 希少性と危険性が競合しているか
- 証拠不足でも判断する意味があるか
- MA-001では高額な委託・出品判断、製品版では高額入札に緊張感があるか
- 見送る判断にも利益があるか
- 正解の開示後ではなく、決断前に考える余地があるか
- 失敗が理不尽ではなく、次の判断材料になるか

情報を全部集めれば常に一意の正解が確定する構造を合格としない。証拠の信頼性、残り時間、資金、危険性、機会費用のうち複数が競合し、プレイヤーが理由を伴う選択を行えることを確認する。

### 判断記録

各周回の決断前に、次を記録する。

```text
迷った選択肢:
最も重視した情報:
不足していた情報:
受け入れた危険:
見送った利益:
決断理由:
結果を知った後に納得できたか:
次回変えたい判断:
```

### 合格条件

- 3セッション中2セッション以上で、結果を見る前に二つ以上の妥当な選択肢を説明できる
- 少なくとも一度、情報・資金・危険性・機会費用の競合を自分の言葉で説明できる
- 失敗後に、次回変える判断材料を一つ以上挙げられる
- PT-S0、PT-S1が0件である

## 7. Playtest Gate 4：継続動機テスト

1回の成功だけでなく、次のオークションへ進みたくなるかを確認する。

- MA-001では研究履歴・信用・人脈、製品版では入手品を蓄積する意味があるか
- 未解明情報が残るか
- 次回の判断に使える知識が増えるか
- 損失を取り返したい気持ちが生まれるか
- 所蔵品、記録、評価、評判などが蓄積されるか
- 同じ操作の繰り返しに見えないか
- 次の出品物に期待を持てるか

「続けたい／続けたくない」だけでなく、その理由と、次に確認したい対象を記録する。

### 合格条件

- 3セッション中2セッション以上で、次に試したい判断または調査を一つ以上挙げられる
- 蓄積された知識、信用、人脈、履歴のうち一つ以上を次回へ使う理由として説明できる
- 同じ操作の反復だけを継続理由にしない
- PT-S0、PT-S1が0件である

## 8. UI評価

各画面を次の観点で0〜4点評価する。

| 評価軸 | 確認内容 |
| --- | --- |
| 目的の明確さ | 何をする画面か |
| 主操作の明確さ | 次に押す場所が分かるか |
| 情報階層 | 重要情報が先に見えるか |
| 可読性 | 文字サイズ、余白、コントラスト |
| 状態表示 | 選択中、処理中、成功、失敗 |
| フィードバック | 操作結果が即座に分かるか |
| 復帰性 | 間違えても戻れるか |
| 判断支援 | 比較に必要な情報が揃うか |

### 点数の意味

| 点 | 判定 |
| ---: | --- |
| 0 | 利用不能、または進行を阻害する |
| 1 | 大きな支援がなければ理解・操作できない |
| 2 | 迷いや誤操作はあるが完了できる |
| 3 | 概ね明確で、軽微な改善余地がある |
| 4 | 初見でも明確で、一貫して判断を支援する |

平均点だけで合否を決めない。重大な問題は高得点の項目で相殺せず、個別のS0またはS1として扱う。

```text
画面名:
目的の明確さ [0-4]:
主操作の明確さ [0-4]:
情報階層 [0-4]:
可読性 [0-4]:
状態表示 [0-4]:
フィードバック [0-4]:
復帰性 [0-4]:
判断支援 [0-4]:
個別ブロッカー:
観察メモ:
```

## 9. 画面サイズと耐久テスト

少なくとも次の条件を分けて確認する。

- 基準解像度
- 小さいウィンドウ
- 高解像度・横長
- 文字量が最大の状態
- 所持品や証拠が大量にある状態
- ボタンが無効、処理中、失敗した状態
- 初回起動と保存データ再開
- 連続して複数オークションを行った状態

各条件で、主操作の到達可能性、横スクロール、二重スクロール、文字欠け、重なり、選択状態の消失、入力内容の消失を確認する。

## 10. 問題の分類

| 重大度 | 定義 | Gate判定 |
| --- | --- | --- |
| **PT-S0 Blocker** | 進行不能、クラッシュ、保存破損、結果不整合 | 即時不合格。後段Gateを停止する |
| **PT-S1 Critical UX** | 主要操作が見つからない、誤操作で重大損失、復帰不能 | 不合格。修正後に同じGateを再実施する |
| **PT-S2 Major** | 目的や結果が分かりにくい、頻繁に迷う | 修正対象。頻度と影響を比較する |
| **PT-S3 Minor** | 文字、余白、表現、軽微な違和感 | バックログへ記録する |
| **Observation** | 不具合ではないが改善余地がある | 仮説として記録し、複数セッションで比較する |

重大度は修正工数ではなく、プレイヤーへの影響で決める。

```text

端末／OS:
解像度・表示倍率:
入力方式:

Playtest Gate 0:

Playtest Gate 2A:
Playtest Gate 2B:
Playtest Gate 3:
Playtest Gate 4:

PT-S0:
PT-S1:
PT-S2:
PT-S3:
Observation:

30秒以内の意味ある操作:

```

正式記録にはCommit SHAを必須とし、異なる実装状態の結果を混在させない。スクリーンショットまたは動画を残す場合は、セッション記録から対応するファイルまたはVisual Logを参照できるようにする。

## 12. 基準の変更

本基準を変更する場合は、変更理由、影響するGate、移行日をGit履歴へ残す。過去の不合格を合格に見せるための閾値変更、テスト除外、問題の重大度引き下げを行わない。
